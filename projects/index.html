CASE 01 · STANDARDS REASONING

CDASH

A Python review pilot that compares study dictionary content with supplied CDASH references and terminology, retaining evidence and presenting reviewer questions rather than automated regulatory verdicts.

THE QUESTION

How can repetitive standards review become more structured without pretending that standards interpretation is fully deterministic?

REVIEW / FIELD 014EVIDENCE ATTACHEDHUMAN REVIEW
STUDY FIELDAdverse Event OutcomeAEOUTInput retained
REFERENCE CONTEXTControlled terminologyEvidence rows linkedReference retained
REVIEW QUESTIONDoes the response set align with the supplied non-extensible terminology?No automatic verdictDecision remains with reviewer
01 / PROBLEM

Manual comparison loses context easily.

Study dictionaries, model guidance and terminology can require field by field review. When the comparison is performed manually, evidence can become separated from the question it supports.

02 / DESIGN DECISION

Create a canonical review layer.

Vendor specific inputs are adapted into a common internal structure so review rules can operate consistently while the original source context remains available.

03 / CONTROL

Fail visibly, not silently.

If a check cannot run or a concept cannot be mapped confidently, the workflow surfaces that condition for review instead of treating absence of a finding as evidence of conformance.

04 / HUMAN BOUNDARY

Questions can be generated. Interpretation cannot be outsourced blindly.

Domain mappings can be proposed and evidence can be assembled, but unmatched concepts remain in a human review queue and nothing writes back to the study dictionary automatically.

WHAT I LEARNED

The safest automation in standards review is often the automation that makes evidence easier to inspect, not the automation that tries to make the final judgment.

Clinical Compliance

THE QUESTION

How do you see participant level patterns when the evidence is distributed across repeated events and multiple sources?

01 / PROBLEM

Flat exports answer record questions, not participant questions.

Repeated AM and PM events can look complete in isolation while timing, sequence or cross source issues only become visible when the participant timeline is reconstructed.

02 / DESIGN DECISION

Normalize events before visualizing them.

Source records are mapped into a consistent event structure first. The dashboard is a review layer on top of that model, not a substitute for the underlying data logic.

03 / CONTROL

Separate missing, incomplete and not expected.

Those states have different operational meanings. Combining them into one missing-data count would create a misleading signal.

04 / HUMAN BOUNDARY

A flag tells the reviewer where to look, not what conclusion to reach.

Compliance logic can identify timing or expected-event exceptions. The reviewer still needs study context before determining whether follow up is required.

WHAT I LEARNED

A dashboard becomes useful only after the data model can explain what a record means in participant and study context.

01 / PROBLEM

Matching values do not guarantee matching records.

Participant identifiers, visit labels, expected record context, timestamps and transfer conventions can differ before the actual result comparison even begins.

02 / DESIGN DECISION

Resolve identity before field comparison.

The workflow first establishes participant, visit and expected record context. Only then are selected fields compared.

03 / CONTROL

Preserve both source values.

A discrepancy remains explicit until reviewed. The workflow does not silently replace one source with another or convert a difference into a correction without context.

04 / HUMAN BOUNDARY

Difference is evidence, not a verdict.

A one minute time difference may require investigation, documentation or no change depending on source provenance and study requirements.

RECONCILIATION FLOW
INGEST SOURCES→STANDARDIZE KEYS→ESTABLISH CONTEXT→COMPARE FIELDS→SURFACE EXCEPTIONS→DOCUMENT DECISION
WHAT I LEARNED

Good reconciliation is not about forcing two sources to agree. It is about making disagreement precise enough for a defensible decision.

Clinical Data

What should be automated when the people doing the work already have established tools and review habits?

01 / PROBLEM

Small repetitive tasks create large operational friction.

Visit mapping, expected dates, lookups and recurring QC can consume review time while also creating opportunities for inconsistent manual handling.

02 / DESIGN DECISION

Choose the smallest tool that fits the workflow.

Excel and VBA can be appropriate when the team already works in spreadsheets. Python becomes more useful when repeated datasets, configuration or reusable pipelines require more structure.

03 / CONTROL

Make assumptions inspectable.

Required inputs, mappings, transformation rules, exceptions and outputs should be understandable to another reviewer rather than hidden inside a black box.

04 / HUMAN BOUNDARY

Automate preparation, not accountability.

The workflow can calculate, transform and flag. The clinical data reviewer remains responsible for interpreting exceptions and deciding what action is appropriate.

WHAT I LEARNED

The best automation is not necessarily the most sophisticated. It is the one a reviewer can trust, understand and use within the real operating environment.
